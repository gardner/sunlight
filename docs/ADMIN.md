# Sunlight Requests Admin App

## Purpose

The admin app at `https://admin.sunlight.nz` is the internal operations surface
for Sunlight's recurring OIA/LGOIMA disclosure collection workflow.

It manages Sunlight's own outbound requests to agencies and the agency responses
to those requests. It does not manage the original OIA/LGOIMA requests made by
members of the public to agencies.

To avoid ambiguity, the product should use these terms consistently:

* `SunlightRequest`: Sunlight's recurring request to an agency asking for that
  agency's OIA/LGOIMA request and response material for a period.
* `SunlightResponse`: An agency's reply to a `SunlightRequest`.
* `DisclosedRequest`: An OIA/LGOIMA request disclosed by an agency in response
  to a `SunlightRequest`.
* `DisclosedResponse`: An agency's OIA/LGOIMA response disclosed in response to
  a `SunlightRequest`.

Phase 0 admin screens should focus only on `SunlightRequest` and
`SunlightResponse` operations. Later document-ingestion jobs can extract
`DisclosedRequest` and `DisclosedResponse` records from stored artifacts.

## Users

Primary admin users are Sunlight operators and technical maintainers.

Operators need to:

* maintain agency records and request contacts
* configure request templates
* create and approve monthly request cycles
* monitor sent, replied, overdue, bounced, and failed cases
* inspect received email and uploaded files
* correct request/response associations
* retry sends and receipt processing

Technical maintainers need to:

* inspect Cloudflare Email, D1, R2, and Worker state
* confirm raw artifacts are preserved
* diagnose failed sends, inbound email handling, and uploads
* export case-level provenance for local processing

## Architecture Boundary

The admin app is a Cloudflare-hosted Vinext app backed by D1 and R2.

D1 stores operational metadata:

* agencies
* request templates
* request cycles
* `SunlightRequest` cases
* outbound email records
* `SunlightResponse` records
* inbound email metadata
* uploaded file metadata
* audit events

R2 stores raw artifacts:

* rendered outbound email snapshots where useful
* raw inbound `.eml` files
* inbound email attachments
* agency-uploaded files
* later parser input/output artifacts

The Cloudflare apps should not perform PDF parsing, OCR, malware scanning beyond
lightweight validation, or legal/redaction review.

## Data Model

The admin data model is the operational engine for Phase 0.

Use `sunlight_*` table names for Sunlight's own collection workflow. Reserve
`disclosed_*` table names for later extraction of the underlying OIA/LGOIMA
request and response records contained in agency submissions.

Phase 0 D1 should store metadata and state. R2 should store raw artifacts and
large files.

### Common Columns

Most mutable tables should include:

* `id`: text primary key, generated by the application
* `created_at`: ISO timestamp
* `updated_at`: ISO timestamp

Operational events should use append-only rows instead of destructive updates
where provenance matters.

Recommended id format:

* public or cross-system ids: `srq_`, `srs_`, `upl_`, `eml_`, `aud_` prefixes
* internal lookup ids may be opaque random text
* avoid sequential public ids in URLs

Statuses:

* `draft`
* `scheduled`
* `queued`

* `bounced`

* `response_received`
* `partially_received`
* `held`
* `failed`

* unique `(agency_id, cycle_id)`
* unique `case_token_hash`

Token strategy:

* Generate a long random `case_token` with at least 128 bits of entropy.
* Store only `case_token_hash` in D1 if practical.
* Store a short `case_token_hint` for operator support, such as the first 6
  characters.
* The agency-facing URL uses the raw token:
  `https://requests.sunlight.nz/response/{case_token}`.
* The reply address should use a unique local part:
  `reply-{case_token}@sunlight.nz`.

If storing only a hash prevents efficient inbound email association, use a
separate random `reply_token` for email and store its hash or encrypted value
with the same care. Do not embed agency names or cycle dates in tokens.

Overdue derivation:

* `is_overdue` should be computed, not stored as canonical state.
* A request is overdue when `expected_due_at` is before today and no qualifying
  closing response has been received.
* Acknowledgements and clarification requests do not clear overdue status by
  default.

### Lifecycle Summary

1. Operator creates agencies and templates.
2. Operator creates a `sunlight_request_cycle`.
3. System creates one `sunlight_request` per included active agency.
4. System generates `case_token`, `reply_email`, and `response_url`.
5. System queues and sends `sunlight_outbound_emails`.
6. Agency replies by email or uploads files.
7. System creates `sunlight_inbound_emails`, `sunlight_uploads`, and
   `sunlight_responses`.
8. Dashboard derives overdue and attention states from current records.
9. Later document-ingestion workers consume R2 artifacts and update processing
   metadata.

## Agency Seed Import

The FYI authority dataset can seed the agency directory, but it is not a
complete sending list because it does not include request contact email
addresses.

Initial seed source:

`~/src/sunlight_nz/fyi/data/all-authorities.csv`

Observed columns:

* `Name`
* `Short name`
* `URL name`
* `Tags`
* `Home page`
* `Publication scheme`
* `Disclosure log`
* `Notes`
* `Created at`
* `Updated at`
* `Version`

Import mapping:

* `Name` -> `sunlight_agencies.name`
* `URL name` -> `sunlight_agencies.slug`
* `Home page` -> `source_metadata_json.home_page`
* `Publication scheme` -> `source_metadata_json.publication_scheme`
* `Disclosure log` -> `source_metadata_json.disclosure_log`
* `Tags` -> `source_metadata_json.tags`
* `Notes` -> `sunlight_agencies.notes`
* `Updated at` -> `sunlight_agencies.source_updated_at`
* fixed `source = fyi`
* fixed `source_id = URL name`
* fixed `source_url = https://fyi.org.nz/body/{URL name}` where appropriate

Import defaults:

* `primary_request_email = null`
* `secondary_request_emails_json = []`
* `contact_status = missing`
* `status = inactive` when tags include `defunct`
* `status = active` otherwise

Legal regime inference:

* use `LGOIMA` for council/local-authority tags such as `district_council`,
  `city_council`, `regional_council`, and explicit `law:lgoima`
* use `OIA` for ministries, departments, universities, Crown entities, DHBs,
  ministers, and explicit `law:OIA`
* use `other` when inference is unclear

The importer should preserve source tags in `source_metadata_json` even when it
infers a legal regime. Operators must be able to correct the regime manually.

Import behavior:

* upsert by `(source, source_id)` when present
* otherwise upsert by `slug`
* never overwrite a verified request email with blank source data
* never downgrade `contact_status = verified` automatically
* preserve local operator notes separately if source notes are refreshed
* write audit events for created agencies and meaningful imported updates

Admin review workflow:

1. Import FYI authorities.
2. Filter agencies by `contact_status = missing`.
3. Operator researches or confirms request email.
4. Operator sets `primary_request_email`.
5. Operator marks `contact_status = verified`.
6. Agency becomes sendable once active and assigned to a template.

The first pilot should use an explicitly reviewed subset rather than every
imported authority.

## Workflow State Machines

Admin actions should be constrained by explicit state transitions. The UI should
show only valid actions for the current state, and the server should enforce the
same rules.

### Request Cycle States

`sunlight_request_cycles.status` transitions:

```text
draft -> previewed -> approved -> sending -> sent -> closed
draft -> closed
previewed -> draft
previewed -> approved
approved -> sending
approved -> closed
sending -> sent
sending -> approved
sent -> closed
```

State meanings:

* `draft`: cycle exists but generated request cases are not final
* `previewed`: operator has generated a preview for active agencies
* `approved`: operator approved the agency list and rendered request plan
* `sending`: outbound email send job is running
* `sent`: send attempts are complete, including failures
* `closed`: cycle is no longer active for normal operations

Only `draft` and `previewed` cycles should allow agency inclusion/exclusion
changes.

### SunlightRequest States

`sunlight_requests.status` transitions:

```text
draft -> scheduled -> queued -> sent -> awaiting_response
queued -> failed
sent -> bounced
sent -> delivered
delivered -> awaiting_response
awaiting_response -> response_received
awaiting_response -> partially_received
awaiting_response -> held
awaiting_response -> closed
response_received -> closed
partially_received -> response_received
partially_received -> held
held -> awaiting_response
failed -> queued
bounced -> queued
closed -> awaiting_response
```

State meanings:

* `draft`: case generated for preview only
* `scheduled`: approved case exists and has token/reply URL
* `queued`: outbound email is queued
* `sent`: provider accepted the outbound send
* `delivered`: provider reported delivery where available
* `bounced`: provider or inbound bounce indicates delivery failure
* `awaiting_response`: request has been sent and no qualifying response has
  closed it
* `response_received`: a qualifying substantive response has been received
* `partially_received`: agency indicated more material will follow
* `held`: operator paused normal workflow
* `failed`: send or operational setup failed
* `closed`: operator considers the case complete

Automatic transitions:

* send queued: `scheduled -> queued`
* provider accepted send: `queued -> sent`
* no bounce after send: `sent -> awaiting_response`
* inbound bounce: `sent|awaiting_response -> bounced`
* qualifying response: `awaiting_response -> response_received`

Operator transitions:

* retry send: `failed|bounced -> queued`
* hold: any active state -> `held`
* unhold: `held -> awaiting_response`
* close: active response states -> `closed`
* reopen: `closed -> awaiting_response`

### SunlightResponse States

`sunlight_responses.status` transitions:

```text
received -> needs_review
received -> accepted
needs_review -> accepted
needs_review -> held
needs_review -> duplicate
needs_review -> rejected
held -> needs_review
accepted -> needs_review
duplicate -> needs_review
rejected -> needs_review
```

State meanings:

* `received`: response metadata exists
* `needs_review`: operator should inspect/categorize it
* `accepted`: response is operationally accepted for the `SunlightRequest`
* `held`: response should not advance workflow
* `duplicate`: response duplicates another response
* `rejected`: response is unrelated or invalid

Accepted response categories can close or advance the parent request depending
on category.

Closing categories:

* `refusal`
* `full_response`
* `no_records_held`
* `transfer_notice`

Non-closing categories by default:

* `acknowledgement`
* `clarification_request`
* `extension_notice`
* `partial_response`
* `follow_up`
* `bounce`
* `unknown`

Operators can override this by closing or holding the parent `SunlightRequest`.

### Upload States

`sunlight_uploads.status` transitions:

```text
pending -> uploading -> uploaded
pending -> abandoned
uploading -> uploaded
uploading -> failed
failed -> pending
uploaded -> held
held -> uploaded
```

Uploads should not automatically close a request unless the agency submits a
response completion choice.

## Deadline And Overdue Rules

Phase 0 should generate expected due dates automatically while allowing operator
override.

Default rule:

* `expected_due_at` is 20 New Zealand working days after the send date.
* Weekends do not count.
* New Zealand national public holidays do not count.
* Regional anniversary days can be ignored in Phase 0 unless an operator
  overrides the date.

If the exact send date is not known when a case is created, compute a provisional
due date from the planned send date and recompute when the email is sent.

Operators can manually change `expected_due_at`. Manual changes must record:

* previous due date
* new due date
* reason
* actor
* timestamp

Due soon:

* a request is due soon when `expected_due_at` is within the next 5 working days
  and the request is not closed or held.

Overdue:

* a request is overdue when `expected_due_at` is before today and the request is
  not closed, held, or accepted as complete.
* acknowledgements do not clear overdue status.
* extension notices should update or prompt review of `expected_due_at`; they do
  not automatically close the request.
* partial responses should move the request to `partially_received` but remain
  overdue after the due date unless an operator changes the due date or closes
  the request.

## Email Sending Semantics

Cloudflare Email Sending is the outbound provider.

Admin status meanings should be conservative:

* `queued`: Sunlight has queued the email locally.
* `sent`: Cloudflare accepted the send request.
* `delivered`: a provider delivery signal was received, if available.
* `failed`: Cloudflare rejected the send request or the Worker failed before
  provider acceptance.
* `bounced`: a bounce email or provider bounce signal was received.

Do not imply guaranteed inbox delivery unless Cloudflare provides a reliable
delivery event.

## Inbound Email Matching

Inbound matching should use a ranked strategy.

Priority:

1. Exact reply address token in the recipient address.
2. Exact response URL token in the email body or headers.
3. Message headers that match a known outbound email.
4. Sender address belongs to an agency with one active awaiting request.
5. Manual operator association.

The Worker should preserve unmatched email in R2 and create an
`association_status = unmatched` metadata row.

Ambiguous matches should never be auto-associated. They should enter triage.

## Manual Correction Model

Operators need correction tools because agencies will reply in inconsistent
ways.

Allowed corrections:

* reassign inbound email to a different `SunlightRequest`
* reassign upload to a different `SunlightRequest`
* create a `SunlightResponse` from an inbound email or upload
* split one inbound email into multiple response records
* merge duplicate responses
* change response category
* change response status
* change request status
* change expected due date
* mark request closed or reopened
* mark material held for review

Every correction must write an audit event with before/after metadata where
practical.

Corrections should not mutate or delete raw R2 artifacts. They should only
change metadata and associations.

## Request Cycles

A request cycle represents a recurring batch, usually monthly.

Fields:

* cycle id
* cycle month
* status: `draft`, `previewed`, `approved`, `sending`, `sent`, `closed`
* created by
* approved by
* approved timestamp
* sent timestamp
* notes

Workflow:

1. Operator creates a monthly cycle.
2. System selects active agencies.
3. Operator previews generated `SunlightRequest` cases.
4. Operator excludes agencies if needed.
5. Operator approves the cycle.
6. System creates immutable case tokens, reply addresses, and response URLs.
7. System queues outbound emails.
8. System records send results and due dates.

Sending must be idempotent per agency and cycle.

## Sunlight Requests

A `SunlightRequest` is one outbound request from Sunlight to one agency for one
cycle.

Fields:

* request id
* agency id
* cycle id
* template id
* case token
* reply email address, for example `reply-{case_token}@sunlight.nz`
* response URL, for example
  `https://requests.sunlight.nz/response/{case_token}`
* status
* expected due date
* overdue status
* sent timestamp
* closed timestamp
* last response timestamp

Statuses:

* `draft`
* `scheduled`
* `queued`
* `sent`
* `delivered`
* `bounced`
* `awaiting_response`
* `response_received`
* `partially_received`
* `held`
* `failed`
* `closed`

Admin list filters:

* cycle
* agency
* status
* legal regime
* due soon
* overdue
* no response
* has uploads
* has inbound email
* failed send

Overdue logic:

* Each `SunlightRequest` stores an `expected_due_at` date.
* A request is overdue when `expected_due_at` is before the current date and no
  qualifying `SunlightResponse` has been received.
* A qualifying response is one categorized as a substantive response, refusal,
  no-records-held response, transfer, or other operator-accepted closing state.
* Acknowledgements and clarification requests should not automatically clear
  overdue status unless an operator marks the case closed or held.

## Inbound Email

Inbound email is received by Cloudflare Email Routing and handled by a Worker.

The Worker should:

* accept routed email
* preserve the raw `.eml` in R2 before any downstream processing
* extract envelope sender/recipient metadata
* extract the reply address token
* associate with a `SunlightRequest`
* create inbound email metadata in D1
* create or update the corresponding `SunlightResponse`
* record an audit event

If the token cannot be associated, the Worker should still preserve the raw
email and mark it as `unmatched`.

## Authentication

The admin app is internal-only.

Use Cloudflare Zero Trust Access in front of `admin.sunlight.nz`.

For Phase 0, Access is the only human login system. The Vinext app should not
implement passwords, magic links, or a parallel Auth.js/NextAuth flow.

Recommended Access policy:

* allow only explicitly listed Sunlight admin email addresses
* use One-Time PIN or a configured identity provider
* keep session duration conservative
* require Access for every route under `admin.sunlight.nz`

Cloudflare Access authenticates the user, then the admin app authorizes the
user.

The app must validate the Access JWT from the `Cf-Access-Jwt-Assertion` header
before trusting any identity headers. Validation should check:

* JWT signature against the Cloudflare Access public keys
* expected issuer for the Sunlight Cloudflare Access team
* expected Access application audience tag for `admin.sunlight.nz`
* token expiry

After validation, the app can use the Access identity claims, especially:

* stable subject id
* email address
* name where available
* identity provider metadata where useful

The app should not trust `Cf-Access-Authenticated-User-Email` unless the JWT has
also been validated for the same request.

Implementation approach:

* create a shared `adminAuth` server helper or Vinext middleware
* reject requests with no valid Access JWT
* look up the authenticated email or subject id in D1
* attach the admin user and role to server-side request context
* write the authenticated identity into audit events

D1 admin user fields:

* id
* access subject id
* email
* display name
* role
* status
* last seen timestamp
* created timestamp
* updated timestamp

Admin authorization roles:

* operator: manage agencies, cycles, requests, responses, uploads
* reviewer: inspect responses and update response state
* maintainer: inspect technical state, retries, and settings

Role checks should be enforced server-side for all mutating actions. Client-side
UI hiding is only a convenience.

Automated processing jobs should not use human Cloudflare Access sessions. They
should use a separate service-to-service path, such as Cloudflare Access service
tokens or narrowly scoped API credentials, with separate audit actor types.

## Non-Goals

The admin app does not:

* publish disclosed material publicly
* perform final legal or redaction decisions
* parse PDFs or OCR documents inline
* expose a public search API
* support arbitrary public OIA request submission
* manage the agency's original requesters as users
